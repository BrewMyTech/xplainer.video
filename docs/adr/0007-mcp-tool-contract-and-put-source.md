# 0007. The MCP tool contract, `put_source`, and JSON Schema as the source of truth

- Status: accepted
- Date: 2026-09-05
- Deciders: @rishavanand
- Settled by: interview rounds 1 and 2 (what the agent hands over; what the hosted tier
  needs on top)

## Context and Problem Statement

An agent — Claude Code or Codex — writes raw Remotion TSX and a narration JSON, then drives
the product through MCP tools: `create → put_source → narrate → still → render`, polling
`job` for the long-running steps. Round 1 established the handover shape by reading the
`max` reference implementation rather than by asking: raw TSX on disk plus
`{voice, speed, fps, langCode?, segments:[{id, text, holdSeconds?}]}`.

Round 2 exposed the gap. `max` runs locally, so its tools assume the agent can write files
to a directory the server can read. **A hosted agent cannot write to a cloud disk.** So the
hosted tier needs a transport for source files that the local tier does not, while spec
§Constraints/Contract simultaneously requires that the tool names and schemas be
**identical** on local and hosted — the agent's skill must not branch on backend.

There is a second problem underneath it. The contract is consumed by TypeScript (the CLI
daemon, the media service) and by Python (the FastAPI control plane). Two hand-maintained
copies of one contract drift, and the drift is invisible until an agent gets a validation
error in production.

## Decision Drivers

- One tool surface, identically named and shaped, on local and hosted (spec
  §Constraints/Contract).
- Two languages must derive from one artefact, or ADR 0002's language split becomes a
  maintenance tax.
- Adding a tool must be a single edit that fails loudly everywhere it is not yet handled.
- Nothing internal to the server should leak to the agent.

## Considered Options

For the source-transport gap:

1. **`explainer_put_source(slug, files[{path, content}])` on both tiers**, with the local
   server *additionally* returning a `write_source_to` path so agents may write files
   directly when they can.
2. **Local-only file paths, hosted-only upload tool** — two different tool sets, and a
   skill that has to know which backend it is talking to.
3. **A pre-signed upload URL** returned by `create`, with the agent doing an HTTP PUT
   outside MCP.

For the contract's source of truth:

4. **JSON Schema in `packages/protocol`, generating TypeScript types and pydantic models.**
5. **TypeScript types as source, generating Python.**
6. **Two hand-written copies kept in sync by review.**

## Decision Outcome

Chosen: **option 1 and option 4.**

**Eight tools, fixed:** `explainer_create`, `explainer_put_source`, `explainer_put_media`,
`explainer_narrate`, `explainer_still`, `explainer_render`, `explainer_job`,
`explainer_list`. `put_source` and `put_media` exist on both tiers; `write_source_to` is an
*optional* field in `explainer_create`'s output, present locally and absent hosted, which
is how one schema covers both without branching the tool set. That is the whole trick of
option 1: the capability difference is expressed as an optional output field rather than as
a different tool.

Option 2 was rejected because it pushes the backend distinction into the skill, which is
the one artefact that must stay backend-agnostic (ADR 0013). Option 3 was rejected for this
phase because it adds an out-of-band HTTP step and a credential to an interaction that MCP
already models perfectly well; it remains a sensible optimisation for large media, which is
why `put_media` carries base64 rather than pretending large files are free.

**JSON Schema is the source of truth** (option 4), at
`packages/protocol/schemas/`: sixteen tool files (input and output for each of the eight),
plus `job-state.json`, `manifest.json`, `narration.json`, `timings.json` and
`captions.json`. `pnpm --filter @xplainer/protocol codegen` regenerates
`src/generated/types.ts` and `python/xplainer_protocol/generated/models.py` in **one
invocation**, so the two languages cannot be regenerated separately, and CI runs the
generator followed by `git diff --exit-code` to fail on stale output.

Option 5 was rejected because it makes one consumer privileged and turns the other into a
second-class derivative. Option 6 was rejected on the driver above.

**Determinism is a requirement here, not a nicety**, because the drift check diffs
generated bytes. `datamodel-code-generator` runs with `--disable-timestamp` — it otherwise
writes a generation timestamp into the file header and *every* diff is dirty — both
generators are pinned to exact versions rather than ranges, and the script sorts its inputs
so filesystem ordering cannot reorder the output. A check that can never pass is
indistinguishable from no check, and gets disabled as noise within a week.

**One deliberate divergence from `max`:** the `explainer_job` output schema **drops the
`command` field** that `max/server/explainer_mcp.py:471` returns. On the hosted backend that
string is the server's internal shell invocation; returning it to an agent leaks host paths
and the render topology for no benefit to the caller. Since local and hosted must expose the
same schema, it is dropped from both.

## Consequences

- **`packages/protocol` is a `uv` workspace member as well as an npm one** (deviation D-1).
  Generating the pydantic models into `apps/api` would have satisfied the letter of the
  spec's uv member list while placing `open-later` artefacts inside a `hosted` package,
  breaking ADR 0003's boundary and the phase-5 extraction.
- **Tool registration iterates `TOOL_NAMES`** rather than listing tools by hand, in
  `packages/mcp-server`'s `createMcpServer()` and in `apps/api`'s `mcp_app.py`. Adding a
  tool to the manifest without implementing it fails a test rather than shipping a surface
  that quietly lacks it.
- **Both MCP surfaces assert against the manifest, never against each other.**
  `apps/api/tests/test_mcp_tools_list.py` and the CLI's `tools/list` Vitest each compare to
  `TOOL_NAMES`; comparing the two servers to one another would let them agree on being
  wrong.
- **Generated output is excluded from Biome** (`!packages/protocol/src/generated/**`), so a
  formatter run cannot make the drift diff dirty, and every emitted file carries a
  "generated — do not edit" header.
- **Schema edits are now a two-command habit**: edit, `codegen`, commit both. CI enforces
  it; the ergonomics cost is real and accepted.
- **The `slug` pattern `^[a-z0-9][a-z0-9-]{0,63}$` is inherited from
  `max/server/explainer_mcp.py:36`** and is what keeps a tool argument from becoming a path
  traversal on either tier.

## Consequences (addendum, 2026-09-05): file ownership is enforced, not requested

The Consequences above treat `explainer_put_source` as a transport: a way to move the agent's
bytes onto a disk the server can read. They say nothing about *which* bytes the agent is
allowed to move, because the reference implementation says nothing either — `max` scaffolds a
stub `Video.tsx` whose doc comment **asks** the agent to keep the audio and caption wiring, and
that request is the only thing standing between an ordinary edit and a silent MP4.

An external architecture review found the defect that follows from it. The scaffolded
`Video.tsx` both draws the picture and mounts `<Audio>` and `<Captions>`. The agent is told to
replace that file wholesale, so a request as small as "make the title smaller" produces a
rewrite, and the two lines a picture-focused rewrite drops are exactly the two that carry the
soundtrack and the captions. Nothing downstream notices: the render succeeds, and a silent,
caption-less video ships. The `slug` pattern and the source-path traversal guard named above do
not help — **path-traversal restrictions establish where a file may be written, never who owns
it**, and the input schema as written here happily accepts `Video.tsx`, `Root.tsx` and
`Captions.tsx` from an agent.

[ADR 0018](0018-engine-owns-the-composition-shell.md) settles it: the composition shell becomes
engine-owned and `explainer_put_source` **refuses** a write to any of five reserved top-level
names. Three things about that change belong in *this* record, because they change this
record's contract rather than merely building on it.

- **The tool contract gains a rejection this record did not anticipate.** `put_source`'s input
  schema gains a `not`/`enum` on `$defs.SourceFile.path`, and a server-side guard rejects the
  whole call — all-or-nothing, nothing written — with an `ENGINE_OWNED_PATH` tool error. The
  guard is registered once in `createMcpServer()`, alongside the `TOOL_NAMES` iteration named
  above and for the same reason: the CLI's stdio surface, the CLI's Streamable HTTP surface and
  the hosted media-service inherit it from one registration, and a future backend cannot forget
  it.
- **The reserved list lives in `packages/protocol/schemas/manifest.json`**, as a new top-level
  `engine_owned_files`, generated into both languages beside `TOOL_NAMES`. This record's rule
  that both surfaces assert against the manifest and never against each other extends to it
  unchanged. `manifest.json` was chosen over a new schema file precisely because the codegen
  pipeline this record describes already excludes it from schema compilation and already emits
  it to TypeScript and Python.
- **`write_source_to` is now a documented hole, not an oversight.** Option 1 above deliberately
  returns a local write path so agents may write files with their own tools; no MCP guard can
  see those writes. That ergonomic win is kept, and the gap is closed at render time instead —
  engine-owned files are derived output, so the render preflight restores any that differ from
  their template and warns. Between a direct write and the next render, a local workspace can
  hold a tampered engine file. That is accepted, and it is the price of the local ergonomics
  this record bought on purpose.

The generated types are **not** the enforcement, and a later reader must not conclude they are:
`json-schema-to-typescript` and `datamodel-code-generator` both ignore `not`, so the generated
TypeScript type and the pydantic model still describe `path` as a plain string. The schema is
the published contract and the ajv gate; the runtime guard is what actually refuses the write.

Python enforcement does not land with ADR 0018 — `apps/api`'s eight tools are still the
placeholders this record describes. Only the generated constant and a pytest pinning it to the
schema land there, so that the day `explainer_put_source` is implemented on the hosted control
plane, the reserved list and the `ENGINE_OWNED_PATH` code string are already in hand. That
obligation is recorded in ADR 0018, and it is the one way the hosted tier could ship without
the guard the local tier has.
